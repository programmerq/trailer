# 0006 — Defer off-GUI-thread PDF open; ship lazy editor/annotation loading first

- **Status:** accepted
- **Arbiter:** the agent role named for this record; the owner (programmerq) is the escalation-only override.
- **Date proposed:** 2026-07-15
- **Date accepted / superseded:** 2026-07-15

> **Update (2026-07-15, follow-on change on `fix/startup-hang-large-pdf`):**
> The annotation sweep (proxy #1, the dominant cost) is no longer merely
> *deferred* on the GUI thread — it now runs entirely **off** the GUI thread
> on an isolated, throwaway qpdf instance loaded from the same path in a
> `QtConcurrent` worker (`PdfDocument::startBackgroundLoad`,
> `src/document/PdfAdapter.cpp`). `annotations()` kicks the worker and returns
> the (initially empty) store immediately; the GUI-thread finished slot commits
> the result via a single batched `AnnotationStore::addBatch`. A fresh qpdf
> instance is used because `QPDF` is not safe for concurrent access (even reads
> mutate its lazy object cache), so the worker shares nothing with the
> GUI-thread `m_editor` — no mutex, no disable-editing.
>
> **Update (2026-07-15, PR #63 owner feedback — editor parse + form detection
> also moved off the GUI thread):** the owner reviewed PR #63 and asked that
> the qpdf editor parse (~0.55s, which `supportsFormFilling()` forced
> synchronously at open to answer the AcroForm probe) NOT block the GUI thread
> — the forms toolbar should become available a moment *after* open rather than
> blocking it. That is now done. The SAME background worker that sweeps
> annotations also parses a **separate, parse-only editor** and reads AcroForm
> presence; on completion the GUI-thread finished slot ADOPTS that editor as
> `m_editor`, caches the forms answer, and fires a `capabilitiesChanged()`
> signal (`CapabilityNotifier`, owned by `PdfDocument`) so
> `MainWindow::onCurrentDocumentChanged` re-runs *only* its forms-toolbar
> enable/populate block (extracted into `refreshFormCapabilities()`).
> `supportsFormFilling()` no longer forces a synchronous parse: it returns a
> provisional `false` ("not ready yet") until the editor is adopted, so the
> forms toolbar is briefly disabled and then enables — G3 disabled-not-lying.
> The sync edit/save paths (`ensureEditorLoaded` / `ensureAnnotationsLoadedSync`)
> block on the in-flight load and adopt its editor if a mutation lands during
> the window (idempotent; `waitForFinished()` does not spin the event loop, so
> no re-entrancy/deadlock). The **only** remaining synchronous open cost is now
> `QPdfDocument::load` (~16ms typical; ~1.8s on the 195MB fixture), the P2
> placeholder item.
>
> **RSS choice (Option B).** The background task keeps the annotation sweep on
> a **throwaway** qpdf instance that is freed before the worker returns (as
> before), and parses a **separate parse-only editor** for adoption — parse
> only, deliberately NOT swept for annotations. Adopting that parse-only editor
> keeps steady-state RSS modest: the adopted `m_editor` never retains the
> fully-resolved ~7.7 GB 1M-annotation graph (that graph lives only on the
> throwaway during the sweep and is released). Option A (adopt the same
> instance used to read annotations) was rejected precisely because it would
> pin that ~7.7 GB graph in `m_editor` for the document's lifetime — a
> steady-state regression on the pathological fixture. The two worker parses
> (throwaway sweep + parse-only adopt) are sequenced so only one large qpdf is
> resident at a time.
>
> **Timings — pathological fixture (`heavy.pdf`, 195MB / 2,500 pages /
> 1,000,000 annotations, generated by `scratchpad/gen.py PAGES=2500 APP=400
> OBJSTREAM=1 AP=1`):** the GUI thread is free after the synchronous open path
> and stays fully responsive (thousands of event-loop ticks) while the
> **~15s isolated** annotation sweep + the editor parse + AcroForm detection
> run on the worker; the batched GUI commit of all 1M annotations costs
> ~125–200ms (a single coalesced refresh). What remains synchronous on the GUI
> thread at open on this fixture is now ONLY `QPdfDocument::load` (~1.8s) — the
> ~0.55s forms parse has moved to the worker (measured: `parseCount()` is 0 the
> instant the synchronous open path returns, and the parse then ticks on a
> worker thread).
>
> **Peak memory (double-live-qpdf sweep, same `heavy.pdf`):** each live qpdf
> that has swept all 1M `/Annots` holds ~7.7 GB resident (measured VmHWM
> 8,073,408 kB for a single-live sweep on a 16 GB container). A *genuine*
> double-live sweep — the throwaway worker qpdf and the GUI-thread `m_editor`
> both resident in a fully-swept 1M state at the same instant — needs ~2×
> that and OOM-kills on a 16 GB container. This is a worst-case upper bound,
> not the steady state: with Option B the adopted `m_editor` is **parse-only**
> and never enters a fully-swept 1M-annotation state, so it is essentially
> never resident at ~7.7 GB alongside the worker's throwaway sweep — the real
> peak sits near the single-live ~7.7 GB. Running two sweeps concurrently also
> *slows* each one — the sweep measures **~41s under concurrent memory pressure
> vs ~15s isolated** — reinforcing that the design keeps the two heavy qpdf
> lifetimes from overlapping in practice.
>
> The full off-thread open + placeholder first page (moving the residual
> `QPdfDocument::load` itself off the GUI thread) remains the P2 follow-up
> (`docs/backlog/2026-07-15-offthread-pdf-open-placeholder.md`); the
> `capabilitiesChanged`-style refresh signal it called for has now landed as
> part of this change.

## Context

Opening a large PDF froze the whole app for minutes (the former
`2026-07-13-startup-hang-large-pdf` P0, closed by #63; residual now tracked in
`docs/backlog/2026-07-15-offthread-pdf-open-placeholder.md`). The
`PdfDocument` constructor ran three synchronous whole-document passes on
the GUI thread before the view existed
(`src/document/PdfAdapter.cpp:146-166`):

The three per-pass figures below are all measured on the **reference
corpus fixture (115MB / ~8,000-page file)** — not the pathological
`heavy.pdf` used for the off-thread timings in the Update note above;
keep the two fixtures distinct when reading these numbers.

1. `QPdfDocument::load(path)` — a bounded progressive read (~16ms on the
   115MB/~8,000-page reference fixture) that yields `pageCount()` + a
   page-0 render. Cheap and lazy inside pdfium. **Kept in the ctor.**
2. `PdfEditor::load(path)` — a full qpdf `QPDF::processFile` parse
   (~29ms on the reference fixture) needed only for editing / forms /
   annotation round-trip.
3. `readAnnotations()` — an all-pages `/Annots` sweep (~137ms on the
   reference fixture, ~75% of open cost) that forces whole-document
   object resolution in qpdf. This is the dominant cost and the
   multi-minute-hang root cause. (On the pathological `heavy.pdf` this
   same sweep is the ~15s isolated worker sweep quantified above.)

The backlog scoped two fix directions: (a) make the editor parse +
annotation sweep lazy, and (b) move `registry.open()` onto a worker
thread with a placeholder first page. It explicitly said the
worker+placeholder was **not** to be implemented "under this item alone."

This change ships (a): passes 2 and 3 are now deferred to first genuine
access via `PdfDocument::ensureEditorLoaded()` /
`ensureAnnotationsLoadedSync()` (`src/document/PdfAdapter.cpp`). The
constructor keeps only pass 1. What remains synchronous on the GUI thread
at open is that residual QPdfDocument bounded progressive read (~16ms).

This record adjudicates whether to also do (b) — moving that residual
read off the GUI thread behind a placeholder — now, or defer it.

## Options

- **A — Defer (b); ship lazy loading only.** Remove the two heavy passes
  from the open path; leave the ~16ms QPdfDocument read synchronous.
  Capture (b) as a separate P2 follow-up
  (`docs/backlog/2026-07-15-offthread-pdf-open-placeholder.md`).
- **B — Do (b) now.** Move `registry.open()` onto a `QtConcurrent`
  worker, render a placeholder first page, and swap in the real view
  when the read completes; flip the `test_perf_gui_thread_io` QSKIP to a
  hard off-thread assertion in the same change.
- **C — Do neither / minimal.** Leave open fully synchronous and only
  document the hang. (Rejected on its face: it ships the P0.)

## Personas debate

- **Office non-technical user:** Opened a big shared PDF and watched the
  app hang with a spinning cursor for minutes — reads it as a crash.
  Cares only that the window becomes usable quickly; does not distinguish
  16ms from instant. Option A already removes the perceptible freeze.
- **Older careful user:** Fears doing something wrong during the hang
  (force-quitting, opening twice). A first paint that arrives promptly
  reassures them; a residual 16ms is imperceptible. No stake in whether
  that last read is on a worker thread.
- **Power migrator:** Opens 200MB scanned/annotated PDFs from another
  tool and expects them to open as fast as that tool. Would eventually
  notice a sub-frame hitch on a truly huge file and want (b) — but not at
  the cost of a regression-prone threading change landing under time
  pressure. Fine with A now, B tracked.
- **Occasional user:** Opens a PDF a few times a month. Unaffected by a
  16ms read; was very affected by a multi-minute hang. A fully covers
  them.

## Admissible objections

- **The dominant cost must never be forced at open** — any user opening a
  large annotated PDF, at construction, hits the ~137ms all-pages sweep
  that triggers the multi-minute hang. Failure: unresponsive window.
  This objection is *binding* and drives keeping proxy #1 (the sweep)
  deferred unconditionally; it is satisfied by A.
- **Power migrator, huge-file open, residual read** — on a 200MB+ file
  the residual QPdfDocument read can still cost more than one frame on
  the GUI thread. Failure: a brief hitch. Real but bounded, and
  addressed by the tracked follow-up (b); does not justify blocking A.

### Rejected as naked preference

- "Open should always be fully threaded on principle." — rejected:
  names no user, step, or failure that A leaves unaddressed; the residual
  read is bounded and the follow-up is tracked.

## Checkable threshold this record would establish

At `DocumentRegistry::open()` on the reference corpus, with the
always-compiled `PdfEditor` instrumentation:

- `PdfEditor::annotationPageVisits() == 0` immediately after open
  (the all-pages sweep did not run at construction), and
- `PdfEditor::parseCount() == 0` at the moment `pageCount()` first
  returns > 0 (the qpdf processFile parse did not run at open).

Both are enforced by `tests/test_perf_lazy_open.cpp`. The off-thread
invariant (`test_perf_gui_thread_io`'s `readThreads()` contains no GUI
thread) stays a documented `QSKIP` until the follow-up lands — this
record does **not** commit to it.

## Arbiter verdict + rationale

**Option A.** The binding objection — the ~137ms all-pages sweep (proxy
#1) must never run at open — is fully satisfied by lazy loading, which
also defers the ~29ms qpdf parse (proxy #2) off the construction path.
That removes the entire perceptible freeze for every persona. The only
objection B additionally answers is the power migrator's bounded
sub-frame hitch on very large files from the residual ~16ms QPdfDocument
read — a real but bounded cost. B is a large, UI-touching, merge-conflict-prone
change (worker thread + placeholder first page + view swap) for that
small residual, and the backlog itself scoped the worker+placeholder out
of "this item alone." Shipping A now retires the P0; B is captured as a
P2 follow-up (`docs/backlog/2026-07-15-offthread-pdf-open-placeholder.md`)
with the `test_perf_gui_thread_io` QSKIP as its acceptance flip.

Residual accepted under A: `MainWindow::onCurrentDocumentChanged` queries
`supportsFormFilling()` and `annotations()` when a document becomes
current. As of the follow-on changes (see the Update notes at the top),
NEITHER runs whole-document work on the GUI thread anymore: `annotations()`
kicks the background worker and returns immediately, and (PR #63)
`supportsFormFilling()` no longer forces the qpdf parse — it returns a
provisional `false` and the parse + AcroForm detection run on that same
worker, with a `capabilitiesChanged()` signal re-running the forms-toolbar
setup once the answer lands. The **only** synchronous open cost left on the
GUI thread is `QPdfDocument::load`. Fully removing that residual read from
the GUI thread (behind a placeholder first page) is exactly the follow-up
(b); the capabilities-refresh signal it required has already landed.

## Evidence required to reopen

A measured, reproducible GUI-thread stall at open attributable to the
residual QPdfDocument read (not the now-lazy passes) on a corpus fixture,
with a wall-clock split showing it exceeds one frame budget — plus owner
sign-off to spend the threading complexity. That evidence would promote
the follow-up (b) from P2 and flip the `test_perf_gui_thread_io` QSKIP to
a live assertion.
